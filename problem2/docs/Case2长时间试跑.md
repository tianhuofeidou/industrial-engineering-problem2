# Case 2高温退火与区间精确重排的长时间试跑

本次在用户提供的30分钟总预算内运行多起点搜索，记录最终完成时间随累计时间的变化。预算包括参数和记录接口准备、算法运行、最后验证与曲线导出；之前10912参考解的计算成本另列，不计入这30分钟，也不声称在本次时刻0重新求得了它。

## 搜索与参数

原退火初温由初始解的64个随机邻居校准：正的目标增量中位数除以`-log(0.8)`。这使中位正增量在原初温下的接受概率约为80%。本次初温乘以2，对同一增量的初始接受概率约为89.4%，允许更充分地探索较差解。

本次降温系数0.97，原对照0.95。每层1000次随机邻域移动；终止温度保持为原校准温度的0.0001倍，不随倍率提高。标准降温流程约326层、326000次移动；同时设90秒上限以服从总预算。接受概率仍为`exp(-增量/温度)`。普通入口默认倍率1和降温0.95，没有静默提高其他旧实验的温度。

第一条流程从已验证10912参考解开始退火，其余流程使用不同种子的贪心构造和完整局部下降，分别完成高温退火与自己的精确阶段。前21分钟任务时间用于多起点，之后集中改善当前最好解。初始种子2026101101，后续每条增加13。

各多起点流程的Gurobi阶段最多110秒，单轮最多5秒、最多80轮，初始区间宽度5。集中改善阶段每次最多100秒、单轮8秒、最多100轮，初始区间宽度轮换5、7、9，并交替采用原约束和精简约束。全部使用8线程与共用环境；每轮仍是独立的受限模型。时间界、到达后换模、工位6完成排序与完整10工位目标保持一致。每次改善完整验证后才更新全局最好值。

预留90秒用于结束、独立验证和图表输出。某轮建模、求解和导出可能造成小幅时间上限误差，实际耗时全部记录，不把单轮TimeLimit称为整个阶段时间。

## 过程记录

入口为`problem2.long_budget`。输出`events.jsonl`逐条追加并刷新，`progress.json`保留当前全局最好值，`summary.json`按阶段保存检查点。每次全局改善在`improvements/bestNNN/`保存完整调度，`best/`保存最新最好方案；输出根目录已经存在时拒绝覆盖。

退火记录每层温度、当前接受解的目标值、退火历史最好值、累计接受数和其中较差解接受数；每次退火改善单独记录。精确阶段记录每轮区间位置、宽度、变量数、实际求解时间、受限下界、状态及前后目标值。

最终`history.json`和`history.csv`包含完整时间线。全局历史最好值应单调不增；退火当前解可以上升。各独立起点重新开始，不能用线连接两次独立退火的当前解，也不能把局部较差解当成全局最好值变差。

`problem2.long_budget_plot`使用已有ReportLab LinePlot图表和PDFium渲染，不新增求解依赖。提供最好值阶梯曲线、退火当前解曲线和温度曲线的PNG/SVG/PDF。`best_curve`包含准备时间；`best_curve_search`只显示实际计算阶段。改善点按退火与Gurobi分别标记；0时刻参考值明确标为本次运行之前已有的方案。曲线源文件的哈希另存`chart_metadata.json`。
